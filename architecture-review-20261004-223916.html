Vocabulary in force. Module = anything with an interface and an implementation. Depth = leverage at the interface, measured as behaviour per unit of interface a caller must learn. Seam = a place behaviour can be altered without editing in that place. Adapter = a concrete thing satisfying an interface at a seam. Locality = change and knowledge concentrating in one place. The deletion test: if deleting a module makes complexity vanish it was a pass-through; if complexity reappears across N callers it was earning its keep. One adapter means a hypothetical seam, two means a real one.

Candidate 1

Deepen the Platform Adapter seam

18 adapters satisfy one 7-method interface that hides six undocumented landmines.

Strong

Files

packages/db/server/services/SchedulerPost.service.ts:180-359 (interface + abstract base)
packages/db/server/services/plugins/*.plugin.ts (18 adapters, 13,147 lines)
packages/scheduler/server/services/AutoPost.service.ts:29-47 (registry)
packages/scheduler/server/services/plugins/{instagram,facebook}.plugin.ts (hottest adapters)

Problem

The seam is declared twice, as a TypeScript interface nobody consumes as a type and as an abstract base class that is the real contract. The interface requires 7 methods and hides six preconditions that are not expressible in it:

  • exposedMethods binds via .bind(plugin, [...arguments]) at :396, shifting every argument. A guard comment at facebook.plugin.ts:77-84 documents a real production outage this already caused.
  • Tokens must be exchanged before publish for Meta page tokens (facebook.plugin.ts:163, TokenRefresh.service.ts:104-107).
  • Two publishDetail shapes are in circulation (:122-152).
  • Cursor pagination differs per adapter (facebook:599, reddit:618, threads:534).
  • Rate limits are per-adapter: reddit sleeps at 1 req/s (reddit:29), x allows 300 posts / 3h (x:18).
  • Error modes split: executeOnPlugins rethrows while callers test response.status === 'failed' (AutoPost:190).

Leverage per unit of interface learned is near zero, because the caller must learn the 7 near-trivial methods plus an undocumented convention set outside them.

Benefits

  • Locality: the six preconditions move out of three unrelated files into the one module that owns them. A Meta token fix becomes one edit.

Candidate 2

Give the ownership invariant one home

40% of database-touching modules re-derive tenancy instead of encoding it.

Strong

Files

packages/db/server/services/*.ts (173 methods take a userId or businessId)
packages/db/server/services/bussines.service.ts:56  ·  review.service.ts:121-135
packages/db/server/services/goal-run.service.ts:43,57,70 vs :85  ·  template.service.ts:41

Problem

173 modules touch a row with a userId. 103 (60%) fold ownership into the same statement. 70 (40%) do not. The invariant is not an interface fact, so every method re-negotiates it:

  • bussines.service.ts:56 — findAll() returns every business profile in the database. A cross-tenant read with no predicate at all.
  • review.service.ts:121-135 — selects by id, then makes a second round trip to verifyBusinessOwnership. Two queries and a race window where one and(...) would have decided it.
  • goal-run.service.ts — the three writes (:43, :57, :70) key on runId alone while the read (:85) scopes by user. Reads and writes of one table disagree about the invariant.
  • template.service.ts:41 — declares userId and never uses it, inserting data.ownerId instead. The interface documents the parameter but not the obligation.

Before / After

flowchart LR subgraph B["Before: invariant re-derived per method"] direction LR C1["caller"] --> M1["findById"] C1 --> M2["update"] C1 --> M3["delete"] M1 --> Q1["SELECT by id"] M1 --> Q2["SELECT ownership, 2nd round trip"] M2 --> Q3["UPDATE by id"] M3 --> Q4["DELETE by id"] end subgraph A["After: invariant behind one seam"] direction LR C2["caller"] --> S["scoped repository"] S --> Q5["WHERE id AND owner"] end

Benefits

  • Locality: the invariant is written once instead of 173 times, so it cannot drift between a read and its neighbouring write.
  • Leverage: every module gains tenancy safety without knowing the predicate shape.
  • Tests: the strongest existing test surface already declares OWNER and OUTSIDER in packages/db/tests/analytics-templates.test.mjs:11. That idiom generalises to one place rather than being re-invented per module.

Candidate 4

Replace module-level registries with a seam that survives code-splitting

The capability registry is deep, but its correctness depends on import order.

Worth exploring

Files

packages/agent/server/capabilities/registry.ts:75-98, 144-182
packages/agent/server/utils/content-api-route.ts:5-22 (14-line compensation comment)
packages/agent/server/flue/skills.ts:35-39, 139, 188, 202-217
packages/agent/server/flue/runtime.ts:76-77, 257

Problem

runCapability(capabilityId, rawInput, ctx) (registry.ts:182) is genuinely deep: schema validation (:115), the approval gate (:126-140), execution and output validation (:198) are all hidden behind one call, and 17 call sites use it. Adding a capability costs 2 files. This is the healthiest seam found in the review.

But its correctness is import-order-dependent. The module doc at :144-156 admits Nitro code-splitting can hand a route its own copy of the registry, leaving it empty and failing 422 CAPABILITY_UNKNOWN. The repair is a registrationEnsured flag (:157) plus a lazy import, and content-api-route.ts:19-22 compensates by importing from a different relative path than index.ts and calling registration explicitly, with a 14-line comment explaining why.

Two further seams leak: CapabilityRender (:17-26) is declared and assigned on capabilities but has zero consumers, and the discovery route at api/v1/agent/capabilities.get.ts:22-72 never calls capabilityRegistry.list(), so the 22 declared capabilities are invisible to every picker. The skills module compounds this with three parallel lookup interfaces over one 15-entry data set, two of them labelled "transitional facets" in its own comments (:35-39).

Problem

A rule honoured by 23% of modules is not a convention, it is a suggestion, and a reader cannot tell which. Worse, the two rules that would catch the most are not wired to anything: scripts/layer-import-audit.mjs is a correct read-only script that exits 1 today, and no workflow in .github/workflows/ runs it, a linter, or any of the repo's 120 test files. .git/hooks/ is empty.

This is not academic. packages/shared/server/services/asset.service.ts is the real Asset implementation, yet it sits in shared and reaches into db for both the schema and the ownership gate. The Asset module has no valid home in the declared graph.

Solution, two honest options

  • Enforce. Add the layer audit and a ServiceResponse lint to CI as non-blocking first, then fix the 14 edges and the 37% of signatures. Costly, and it front-loads a large diff.
  • Narrow. Amend AGENTS.md:16 to say the convention applies to new modules, wire the layer audit into CI because it is already written and correct, and let the existing 37% be grandfathered. Cheap, honest, and it stops the documentation from lying.

This candidate also needs an ADR. Layer placement is exactly the kind of decision a future explorer will otherwise re-litigate, and there is currently no ADR directory at all.

Top recommendation

Candidate 1, the Platform Adapter seam

It is where the churn already is. Five of the last 24 commits touch an adapter. Commit 0514329c added 27 lines of Meta page-token branching directly into the publish path, and 49a89c17 fixed an account-id trap in the same module. That is the signature of missing depth: the same knowledge needed re-entering from a different direction each time.

It has 18 adapters, so the seam is already real. By the two-adapter test this is not a speculative abstraction to invent, it is a genuine seam carrying real duplication: 16 copies of one method, 3 places re-deriving Meta token renewal, 9 adapters bypassing a helper the other 11 use.

It is the only candidate with a concrete defect attached. The exposedMethods argument shift has already caused one production failure, documented in a scar-tissue comment at facebook.plugin.ts:77-84. That is the seam failing, not an implementation bug, and it will happen again.

Why not the others first. Candidate 2 is the largest safety win and I would not argue against doing it, but 173 methods make it a multi-week change with a large review surface, so it benefits from the enforcement in candidate 6 landing first. Candidate 3 is well-scoped and could go in parallel. Candidate 4 is a live 422 risk that deserves a ticket regardless of whether the refactor happens. Candidate 1 is the one that makes the others cheaper, because the Platform rules in candidate 3 are the same vocabulary the adapters currently own privately.

Negative results worth recording

  • No table is dead. A reference audit of all 63 tables found 4 with no app reference, and all 4 are better-auth framework tables that must stay. One genuinely dead module was found and removed earlier this session: subscriptions and its 441-line module.
  • The persistence layer is not a seam, but the tests already work around it well. useDrizzle takes zero parameters across 71 call sites, yet packages/db/tests/setup.mjs:33 substitutes a real adapter for all 19 test files through one globalThis swap. That is a working substitution point with genuine locality. It is just invisible in every implementation's signature, which is why it did not become a candidate on its own.
  • The best test surface in the repo is the db package. 19 files stand up a migrated file-backed database and call implementations directly, and one already declares OWNER and OUTSIDER to assert tenancy. That idiom is the model the other candidates would follow.
